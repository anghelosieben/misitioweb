¿Qué es Git?

Git es un sistema de control de versiones que permite registrar los cambios en archivos a lo largo del tiempo. Pero no es solo un registro de cambios: es una máquina del tiempo para tu código, un laboratorio de experimentación, y un sistema de colaboración todo en uno.

La diferencia fundamental entre Git y otros sistemas de control de versiones es su arquitectura distribuida. Cada desarrollador tiene una copia completa del repositorio, incluyendo toda su historia. Esto significa que puedes trabajar sin conexión, comparar cambios localmente, y colaborar de formas que no eran posibles antes.

"Git thinks of data as a stream of snapshots of a miniature filesystem."

Cada vez que guardas un estado en Git ( haces un commit ), él toma una foto de todos tus archivos en ese momento y guarda una referencia a esa foto. Si un archivo no cambió, Git no lo almacena de nuevo, solo crea un enlace al archivo idéntico anterior.

Conceptos Fundamentales

Repositorio

Un repositorio es simplemente una carpeta que Git rastrea. Contiene todos los archivos de tu proyecto y la historia de sus cambios. Puede ser local (en tu computadora) o remoto (en un servidor como GitHub o GitLab).

Snapshots (Instantáneas)

A diferencia de otros sistemas que guardan diferencias (deltas), Git guarda instantáneas completas del estado de tu proyecto en cada commit. Esto hace que operaciones como cambiar de rama o revisar historial sean extremadamente rápidas.

Hash SHA-1

Cada objeto en Git se identifica con un hash SHA-1 de 40 caracteres. Este hash es único para cada contenido, lo que significa que Git puede detectar corrupiones o conflictos sin ambigüedad.

Integridad

Todo en Git es verificable mediante sumas de verificación (checksums). No puedes perder información durante una transferencia o corrupión de disco sin que Git lo detecte.

Las Tres Áreas

Git organiza tu trabajo en tres áreas conceptually diferentes. Entender cómo se mueven los archivos entre ellas es fundamental para dominar Git.

Directorio de Trabajo (Working Directory)

Es la carpeta donde trabajas normalmente. Aquí ves y editas tus archivos. Los cambios aquí aún no están siendo rastreados por Git, o pueden estar modificados respecto a la última foto guardada.

El directorio de trabajo es una copia de una versión específica del proyecto, extraída del repositorio para que puedas trabajar sobre ella.

Área de Preparación (Staging Area)

El área de preparación, también llamada índice, es un archivo que almacena qué irá en tu próximo commit. Es como una lista de compras: preparas exactamente qué quieres incluir antes de confirmar los cambios.

Esta área te da control granular sobre qué cambia exactamente en cada commit. Puedes incluir solo ciertos archivos, o incluso solo partes de un archivo.

Repositorio Git

Aquí Git guarda las instantáneas de forma permanente. Es la base de datos de tu proyecto, donde toda la historia de commits vive. Cuando говорят de "guardar" en Git, se refiere a mover cambios del área de preparación al repositorio.

El flujo básico es: modificar archivos en el directorio de trabajo, añadir los cambios que quieres al área de preparación, y luego confirmar (commit) esos cambios al repositorio.

Commits

Un commit es la unidad básica de trabajo en Git. Representa una foto del proyecto en un momento específico. Cada commit tiene un mensaje que describe qué cambios se hicieron y por qué.

Anatomía de un Commit

Commit Hash: a1b2c3d4...

Autor: Tu Nombre <tu@email.com>

Fecha: Thu Apr 5 10:30:00 2026

Mensaje: Agregar validación de formulario

Puntero al commit anterior: parent: a1b2c3d4...

Cada commit指向 un commit anterior (excepto el primero, que no tiene padre). Esta cadena de commits es lo que forma la historia de tu proyecto.

Mensajes de Commit

Un buen mensaje de commit es crucial para navegar la historia del proyecto. Debe ser descriptivo pero conciso, explicando el "qué" y el "por qué", no el "cómo".

Un buen mensaje: "Agregar validación de email en formulario de registro"

Un mal mensaje: "Cambios" o "WIP" o "Fix bug #123"

Ramas (Branches)

Las ramas son una de las características más poderosas de Git. Una rama es simplemente un puntero móvil a un commit específico. Cuando creas una nueva rama, Git crea un nuevo puntero que puedes mover independientemente de otras ramas.

La rama principal se llama usualmente "main" o "master". Pero no hay nada especial en ella: es solo otra rama. La diferencia es que por convención representa la línea de desarrollo estable.

Trabajo en Paralelo con Ramas

main
nueva-funcionalidad

¿Por qué Ramas?

Las ramas permiten trabajar en paralelo sin interferir con el trabajo de otros. Puedes experimentar libremente, saber que tu trabajo actual no romperá la versión estable del proyecto. Cuando estás satisfecho, fusionas los cambios de vuelta.

Esta forma de trabajar es radicalmente diferente al modelo lineal, donde los desarrolladores trabajan en secuencia sobre la misma base de código, frecuentemente bloqueándose unos a otros.

Ramas y Punteros

En Git, crear una rama es increíblemente ligero. No copia archivos, no consume mucho espacio. Una rama es simplemente un archivo de 41 bytes (aproximadamente) que contiene un hash SHA-1.

Cuando haces commits en una rama, el puntero de la rama avanza automáticamente. Si creas una rama desde un commit que tenía 10 archivos idénticos a main, Git no copia nada. Solo crea un nuevo puntero al mismo commit.

HEAD

HEAD es un puntero especial que indica dónde estás trabajando actualmente. Usualmente apunta a una rama, pero también puede apuntar directamente a un commit (estado de "detached HEAD").

Flujo de Trabajo Común

No existe un único flujo de trabajo con Git, pero hay patrones que la mayoría de equipos siguen. El más común involucra una rama principal protegida y ramas de característica.

Git Flow

Este flujo usa dos ramas principales: main (para releases) y develop (para integración). De develop se crean ramas de característica que luego vuelven a develop. Las releases se fusionan de develop a main.

Este modelo funciona bien para proyectos con ciclos de release regulares, pero puede ser overkill para proyectos más simples o equipos pequeños.

GitHub Flow

Un flujo más simple: solo existe main como rama principal. Para trabajar en algo, creas una rama desde main, haces tus cambios, y cuando están listos, abres un pull request para revisarlos y fusionarlos.

Este modelo requiere que main siempre esté listo para deploy. Es ideal para proyectos con integración y deployment continuos.

El Ciclo Básico

git checkout -b nueva-funcionalidad Crear y cambiar a nueva rama

git add archivo.js Preparar archivos modificados

git commit -m "Mensaje" Guardar cambios

git push origin nueva-funcionalidad Subir al remoto

git pull request Solicitar revisión y fusión

Fusión (Merge) vs Rebase

Cuando necesitas combinar trabajo de dos ramas, hay dos formas principales de hacerlo. Merge crea un commit especial que une dos historias. Rebase reescribe los commits de una rama como si hubieran partido de otro punto.

Merge

Merge toma los cambios de una rama y los aplica sobre otra, creando un commit de fusión. Preserve la historia original y es seguro, pero puede hacer el historial más difícil de seguir.

Rebase

Rebase "reproduce" tus commits como si hubieran sido hechos sobre la última versión de la otra rama. Crea un historial lineal más limpio, pero reescribe historia, así que nunca debe hacerse en ramas compartidas.

Reflexión

Git es una herramienta poderosa que cambia fundamentalmente cómo piensas sobre el desarrollo de software. Con Git, los errores dejan de ser temibles porque siempre puedes volver atrás. La experimentación se vuelve segura porque puedes crear ramas sin riesgo.

"Git es como una máquina del tiempo, un laboratorio de experimentación, y una red social para desarrolladores, todo en uno."

Dominar Git toma tiempo. Los comandos son simples, pero la comprensión profunda viene con la práctica. No te preocupes si al principio cometes errores: Git es muy difícil de romper algo permanentemente, y los comandos de "deshacer" son generosos.

Lo más importante no es memorizar cada comando, sino entender los conceptos fundamentales: cómo Git piensa sobre los datos, cómo las ramas funcionan, y cómo los cambios fluyen entre áreas. Con esa base, el resto viene naturalmente.
