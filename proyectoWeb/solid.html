Introducción

SOLID es un acrónimo que representa cinco principios de diseño de software orientados a objetos. Fueron popularizados por Robert C. Martin (Uncle Bob) y ayudan a crear código más mantenible, flexible y extensible.

S
Single Responsibility

Una clase, una responsabilidad

O
Open/Closed

Abierto para extensión, cerrado para modificación

L
Liskov Substitution

Sustitución sin alterar correctitud

I
Interface Segregation

Interfaces específicas, no generales

D
Dependency Inversion

Depender de abstracciones

¿Por qué usar SOLID?

Estos principios ayudan a evitar code smells, reducir complejidad, facilitar el refactoring y hacer el código más testeable y mantenible a largo plazo.

S Single Responsibility Principle

Responsabilidad Única

Una clase debe tener una sola razón para cambiar. Esto significa que una clase debe tener solo un trabajo o responsabilidad.

Problema

MAL Usuario.java 
public class Usuario {
    private String nombre;
    private String email;

    public Usuario(String nombre, String email) {
        this.nombre = nombre;
        this.email = email;
    }

    // Responsabilidad 1: Persistencia
    public void guardar() {
        System.out.println("Guardando en base de datos...");
    }

    // Responsabilidad 2: Envío de emails
    public void enviarEmail(String mensaje) {
        System.out.println("Enviando email: " + mensaje);
    }

    // Responsabilidad 3: Generación de reportes
    public void generarReporte() {
        System.out.println("Generando reporte PDF...");
    }

    // Responsabilidad 4: Validación
    public boolean validar() {
        return this.email.contains("@");
    }
}

// Esta clase tiene 4 razones para cambiar!
// Si cambia el formato del reporte, modificamos Usuario
// Si cambia el SMTP, modificamos Usuario

class Main {
    public static void main(String[] args) {
        Usuario usuario = new Usuario("Juan", "juan@email.com");
        usuario.guardar();
        usuario.enviarEmail("Bienvenido");
        usuario.generarReporte();
    }
}

Solución

BIEN SRPSolucion.java 
// SRPSolucion.java
// Cada clase tiene UNA responsabilidad

public class Usuario {
    private String nombre;
    private String email;

    public Usuario(String nombre, String email) {
        this.nombre = nombre;
        this.email = email;
    }

    public String getNombre() { return nombre; }
    public String getEmail() { return email; }
}

class UsuarioRepositorio {
    public void guardar(Usuario usuario) {
        System.out.println("Guardando usuario en BD: " + usuario.getNombre());
    }

    public Usuario buscar(String id) {
        return null;
    }
}

class EmailService {
    public void enviar(Usuario usuario, String mensaje) {
        System.out.println("Enviando email a " + usuario.getEmail());
    }
}

class ReporteService {
    public void generar(Usuario usuario) {
        System.out.println("Generando reporte PDF para: " + usuario.getNombre());
    }
}

class Main {
    public static void main(String[] args) {
        Usuario usuario = new Usuario("Juan", "juan@email.com");
        
        UsuarioRepositorio repo = new UsuarioRepositorio();
        EmailService emailSvc = new EmailService();
        ReporteService reporteSvc = new ReporteService();

        repo.guardar(usuario);
        emailSvc.enviar(usuario, "Bienvenido");
        reporteSvc.generar(usuario);
    }
}

Beneficios:

Cada clase es más pequeña, fácil de entender, testar y mantener. Los cambios en un dominio no afectan a los otros.

O Open/Closed Principle

Abierto/Cerrado

Las entidades de software (clases, módulos, funciones) deben estar abiertas para extensión pero cerradas para modificación.

Problema

MAL CalculadoraMal.java 
class Circulo {
    public double radio;
    public Circulo(double radio) {
        this.radio = radio;
    }
}

class Cuadrado {
    public double lado;
    public Cuadrado(double lado) {
        this.lado = lado;
    }
}

// MAL: Cada vez que agregamos una nueva figura,
// debemos modificar esta clase
class CalculadoraArea {
    public double calcular(Object figura) {
        if (figura instanceof Circulo) {
            return Math.PI * ((Circulo) figura).radio * ((Circulo) figura).radio;
        } else if (figura instanceof Cuadrado) {
            return ((Cuadrado) figura).lado * ((Cuadrado) figura).lado;
        }
        throw new IllegalArgumentException("Figura no soportada");
    }
}

class Main {
    public static void main(String[] args) {
        CalculadoraArea calc = new CalculadoraArea();
        System.out.println("Circulo: " + calc.calcular(new Circulo(5)));
        System.out.println("Cuadrado: " + calc.calcular(new Cuadrado(4)));
    }
}

Solución

BIEN OCPSolucion.java 
// OCPSolucion.java
// Usamos abstracción para cerrar la modificación

interface Figura {
    double calcularArea();
}

class Circulo implements Figura {
    private double radio;

    public Circulo(double radio) {
        this.radio = radio;
    }

    @Override
    public double calcularArea() {
        return Math.PI * radio * radio;
    }
}

class Cuadrado implements Figura {
    private double lado;

    public Cuadrado(double lado) {
        this.lado = lado;
    }

    @Override
    public double calcularArea() {
        return lado * lado;
    }
}

class CalculadoraArea {
    public double calcular(Figura figura) {
        return figura.calcularArea();
    }
}

// Agregar Triangulo es fácil, sin modificar CalculadoraArea
class Triangulo implements Figura {
    private double base;
    private double altura;

    public Triangulo(double base, double altura) {
        this.base = base;
        this.altura = altura;
    }

    @Override
    public double calcularArea() {
        return (base * altura) / 2;
    }
}

class Main {
    public static void main(String[] args) {
        CalculadoraArea calc = new CalculadoraArea();

        System.out.println("Circulo (r=5): " + calc.calcular(new Circulo(5)));
        System.println("Cuadrado (l=4): " + calc.calcular(new Cuadrado(4)));
        System.out.println("Triangulo (b=6, a=3): " + calc.calcular(new Triangulo(6, 3)));
    }
}

Clave: Usa herencia, polimorfismo e interfaces para extender comportamiento sin modificar código existente.

L Liskov Substitution Principle

Sustitución de Liskov

Los objetos de una subclase deben poder sustituir objetos de la clase padre sin afectar la correctitud del programa.

Problema

MAL AveMal.java 
class Ave {
    public void volar() {
        System.out.println("Volando...");
    }
}

class Pinguino extends Ave {
    @Override
    public void volar() {
        throw new RuntimeException("Los pingüinos no vuelan!");
    }
}

class Main {
    public static void main(String[] args) {
        Ave[] aves = { new Ave(), new Pinguino() };
        
        for (Ave ave : aves) {
            ave.volar(); // Falla con Pinguino!
        }
    }
}

Solución

BIEN LSPSolucion.java 
// LSPSolucion.java
// Separar en interfaces según capacidades

interface Volador {
    void volar();
}

interface Nadador {
    void nadar();
}

class Ave {
    private String nombre;

    public Ave(String nombre) {
        this.nombre = nombre;
    }

    public String getNombre() { return nombre; }
}

class Pinguino extends Ave implements Nadador {
    public Pinguino(String nombre) {
        super(nombre);
    }

    @Override
    public void nadar() {
        System.out.println(getNombre() + " nadando...");
    }
}

class Aguila extends Ave implements Volador {
    public Aguila(String nombre) {
        super(nombre);
    }

    @Override
    public void volar() {
        System.out.println(getNombre() + " volando alto!");
    }
}

class Main {
    public static void main(String[] args) {
        Volador[] voladores = { new Aguila("Aguila Real") };
        
        System.out.println("=== Voladores ===");
        for (Volador volador : voladores) {
            volador.volar();
        }

        System.out.println("=== Nadadores ===");
        Nadador[] nadadores = { new Pinguino("Pinguino Emperador") };
        for (Nadador nadador : nadadores) {
            nadador.nadar();
        }
    }
}

Regla: Si una subclase no puede cumplir completamente el contrato de su clase padre, no debería heredar de ella. Mejor usar composición o interfaces.

I Interface Segregation Principle

Segregación de Interfaces

Es mejor tener muchas interfaces específicas que una interfaz general. Los clientes no deben depender de métodos que no usan.

Problema

MAL MaquinaPesada.java 
// Interfaz muy grande y acoplada
interface IMaquina {
    void imprimir();
    void escanear();
    void fax();
    void fotocopiar();
}

// Esta clase debe implementar todos los métodos,
// aunque solo use imprimir
class ImpresoraSimple implements IMaquina {
    @Override
    public void imprimir() {
        System.out.println("Imprimiendo documento");
    }

    @Override
    public void escanear() {
        // No necesito esto pero debo implementarlo
    }

    @Override
    public void fax() {
        // No necesito esto pero debo implementarlo
    }

    @Override
    public void fotocopiar() {
        // No necesito esto pero debo implementarlo
    }
}

class Main {
    public static void main(String[] args) {
        IMaquina maquina = new ImpresoraSimple();
        maquina.imprimir();
    }
}

Solución

BIEN ISPSolucion.java 
// ISPSolucion.java
// Interfaces pequeñas y cohesivas

interface Impresora {
    void imprimir(String documento);
}

interface Escaner {
    String escanear();
}

interface Fax {
    void fax(String numero, String contenido);
}

// Cada clase solo implementa lo que necesita
class ImpresoraSimple implements Impresora {
    @Override
    public void imprimir(String documento) {
        System.out.println("Imprimiendo: " + documento);
    }
}

// Multifuncional implementa múltiples interfaces
class Multifuncional implements Impresora, Escaner, Fax {
    @Override
    public void imprimir(String documento) {
        System.out.println("Imprimiendo (MF): " + documento);
    }

    @Override
    public String escanear() {
        System.out.println("Escaneando documento");
        return "contenido escaneado";
    }

    @Override
    public void fax(String numero, String contenido) {
        System.out.println("Enviando fax a " + numero);
    }
}

class Main {
    public static void main(String[] args) {
        Impresora simple = new ImpresoraSimple();
        simple.imprimir("Documento simple");

        System.out.println("---");

        Multifuncional mf = new Multifuncional();
        mf.imprimir("Documento MF");
        mf.escanear();
        mf.fax("123-456", "Mensaje fax");
    }
}

Ventaja: Interfaces pequeñas son más fáciles de implementar, entender y mantener. Los cambios en una parte no afectan a las demás.

D Dependency Inversion Principle

Inversión de Dependencias

Las clases de alto nivel no deben depender de clases de bajo nivel. Ambas deben depender de abstracciones. Las abstracciones no deben depender de detalles; los detalles deben depender de abstracciones.

Problema

MAL AcoplamientoDirecto.java 
// Clase de bajo nivel
class MySQLDatabase {
    public void conectar() {
        System.out.println("Conectando a MySQL");
    }

    public void query(String sql) {
        System.out.println("Ejecutando: " + sql);
    }
}

// Clase de alto nivel depende directamente de bajo nivel
// Problema: Si cambiamos de MySQL a PostgreSQL,
// debemos modificar UsuarioService
class UsuarioService {
    private MySQLDatabase db = new MySQLDatabase();

    public void guardar(String nombre) {
        db.conectar();
        db.query("INSERT INTO usuarios (nombre) VALUES ('" + nombre + "')");
    }
}

class Main {
    public static void main(String[] args) {
        UsuarioService service = new UsuarioService();
        service.guardar("Juan");
    }
}

Solución

BIEN DIPSolucion.java 
// DIPSolucion.java

// 1. Crear abstracción (interfaz)
interface IRepositorio {
    void conectar();
    void query(String sql);
}

// 2. Implementaciones concretas
class MySQLRepositorio implements IRepositorio {
    @Override
    public void conectar() {
        System.out.println("MySQL conectado");
    }

    @Override
    public void query(String sql) {
        System.out.println("MySQL: " + sql);
    }
}

class PostgreSQLRepositorio implements IRepositorio {
    @Override
    public void conectar() {
        System.out.println("PostgreSQL conectado");
    }

    @Override
    public void query(String sql) {
        System.out.println("PostgreSQL: " + sql);
    }
}

// 3. Clase de alto nivel depende de abstracción
class UsuarioService {
    private IRepositorio repositorio;

    public UsuarioService(IRepositorio repositorio) {
        this.repositorio = repositorio;
    }

    public void guardar(String nombre) {
        repositorio.conectar();
        repositorio.query("INSERT INTO usuarios (nombre) VALUES ('" + nombre + "')");
    }
}

class Main {
    public static void main(String[] args) {
        System.out.println("=== Con MySQL ===");
        UsuarioService serviceMySQL = new UsuarioService(new MySQLRepositorio());
        serviceMySQL.guardar("Juan");

        System.out.println("=== Con PostgreSQL ===");
        UsuarioService servicePostgres = new UsuarioService(new PostgreSQLRepositorio());
        servicePostgres.guardar("Maria");
    }
}

Beneficios: Código más testeable (podemos mockear el repositorio), flexible para cambiar implementaciones, y bajo acoplamiento.

Resumen

Principio Descripción Corta Problema que Resuelve
SRP Una clase, una responsabilidad Clases sobrecargadas, difícil de mantener
OCP Abierto para extensión, cerrado para modificación Modificar código existente causa errores
LSP Sustitución sin romper el programa Herencias que no cumplen el contrato
ISP Interfaces específicas > interfaces generales Clases forzadas a implementar métodos inútiles
DIP Depender de abstracciones, no concreciones Alto acoplamiento, difícil de testeable

Aplicación Práctica:

No se trata de aplicar todos los principios ciegamente, sino de entender cuándo cada uno mejora tu diseño. El objetivo siempre es código mantenible, testeable y extensible.

1
Empieza Simple

No sobre-diseñes. Aplica SOLID cuando haya necesidad.

2
Refactoriza Incrementalmente

Mejora el código existente poco a poco cuando trabajes en él.

3
Prioriza la Abstracción

Usa interfaces para definir contratos claros entre módulos.
